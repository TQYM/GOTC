# CITY20 像素风 UI 与 3D 地图重构：Claude 工作交接

> **状态：未完成的工作快照，不能直接合并。** 用户批准的是当前视觉方向，明确要求保留真正的 3D 操作和现有游戏逻辑。本文件记录 2026-11-08 的对话、代码及核验结果，接手时应先重新检查远端状态。

## 1. 用户要 Claude 做什么

用户最初要求：基于远端 `main` 建 worktree，分析并重构项目的前端 UI 和地图场景外观，使 UI 具有适合游戏的、轻松活泼的像素风，并让地图场景的建模、材质与配色匹配 UI。

用户先要求制作视觉稿；Claude 展示了主界面、建造背包和建筑详情三张画面。落地页及设计规范两个画框当时仍为空。用户看过后明确说：

> 这是个3d操作的项目，你做的是2d游戏，不是重构整个项目的逻辑。不过现在的视觉稿没问题，挺好看的，可以开工了

因此后续应把视觉稿当作**色彩、图标和 HUD 风格的参考**，将这种风格应用到现有的真 3D 沙盘，而不是把地图或交互改成 2D 游戏。保留相机操作、真实北京地图、建筑点选/建造/拆除、城市模拟与存档等现有功能；AI 仍只承担叙述，前后端契约仍以 [`02-data-contract.md`](../plan/02-data-contract.md) 为准。

## 5. 最高优先级：接入最新 main，保住全北京地图

以 `origin/main@5b00021` 和代码快照 `78ff844` 做过**不修改工作树**的合并模拟，出现 5 个实际内容冲突：

1. `frontend/src/app/globals.css`
2. `frontend/src/app/sandbox/SandboxView.tsx`
3. `frontend/src/components/game/GameView.tsx`
4. `frontend/src/components/scene/CityScene3D.tsx`
5. `frontend/src/components/scene/RealCityLayers.tsx`

下一位接手者应先获取最新 `main` 并以项目协作约定安全整合，逐项解决冲突，不能用一侧整体覆盖另一侧。`main` 的 PR-36 在 `CityScene3D` 引入全域地图图层、LOD、地图拾取、地名和建筑面板等；旧草稿的色板及 `PixelPass` 主要作用于较早的片区场景。全域地图的 `MapLayers` 还有独立的地形纹理、顶点色和材质，不能假定更换旧片区色板就已经统一了全图。全域 `MapLabels` 使用 DOM 覆盖层，而旧草稿中片区标签采用 Three.js 图层，整合像素渲染时应分别检查两者。

需要同时保住：真实北京全域与 CBD 片区、3D 摄像机/LOD、地图和沙盘拾取、建筑信息面板、放置/拆除与地块坐标；再在两种地图视图上检查同一视觉方向。注意验证全域覆盖层、相机图层及渲染状态切换，不要只解决文本冲突就宣称功能兼容。

## 6. 剩余工作与验收顺序

1. **合入最新 `main`，完成上述冲突和 PR-36 适配。** 阅读 `docs/plan/00-master.md`、`docs/plan/08-pr-tasks.md` 及相关地图文档，保留旧版片区和新版全域地图功能；确认全图颜色/材质、DOM 地名与 `PixelPass` 的配合。
2. **修复 lint。** 针对 `PixelPass.tsx` 的两个具体错误处理 renderer 状态及 uniform 更新；确认在启用、关闭、重新挂载和尺寸变化时渲染资源与状态正确。不要为了过 lint 破坏渲染或盲目抑制规则。
3. **补齐浏览器与触屏验收。** 桌面及 375px 手机宽度检查布局、文字、弹窗、抽屉和视口溢出；分别在像素度关闭、2×、3× 下验证相机移动旋转缩放、点击与触屏拾取、建筑放置/拆除落在正确格子，并核对地图选择与标签。
4. **回归主流程。** 按 [`07-qa-ops.md`](../plan/07-qa-ops.md) 跑创建/加入、建造、快进、推演、报告、继续经营与历史回看；验证无 LLM key 的降级链路及已有存档/同步功能没有回退。核查 `data-testid` 和关键 `aria-*`，不能仅凭当前测试通过断定全部保留。
5. **测量性能并留证。** 按设计草案记录 CBD 的 FPS 与 draw call 基线/改造后结果（草案目标为桌面 ≥50 FPS、描边增量 ≤8），同时针对新版全域地图单独测量 LOD、加载和交互性能；手机端按对应地图和设备条件记录，未测不要标为通过。
6. **修订文档与素材声明。** 更新 `docs/screenshots/` 的手机和桌面图；修订 `16-pixel-art-ui.md`，并按仓库“任务卡在 08”的约定将 PR-39～42 与 [`08-pr-tasks.md`](../plan/08-pr-tasks.md) 对齐。检查 [`docs/SOURCES.md`](../SOURCES.md) 与分发许可声明。
7. **最终验证并提交 PR。** 在符合仓库构建目录约定的隔离环境运行 `npm ci`、`npm test`、`npm run lint`、`npm run build`；必要时按 CI 检查后端。完成各任务卡 DoD、CI 和审查后再合并，PR 描述写清实际测试与剩余风险。

## 7. 设计文档与实现目前不一致的地方

- 设计草案写中文字体 **Fusion Pixel**、静态字表子集和动态字库懒加载；实际依赖是 **Pixelify Sans + 站酷庆科黄油体**，尚未证明草案中的子集化方案已实现。Claude 当时称选择与视觉稿一致，且计划文档需要更新；字体来源和许可证仍应核验并记录。
- 设计草案写功能图标使用 **pixelarticons**；现代码为自绘像素图标和程序生成的建筑缩略图。应以审查后的实际实现修正文档及来源声明，不要误写成已引入 pixelarticons。
- 草案列有 PR-39～42，但交接时这几张卡尚未追加到 `08-pr-tasks.md`。草案各 DoD 仍为未勾选，不能因本分支有代码就标为完成。
- 草案的 `civic` 颜色仍为粉色；代码已改为中性奶油色。像素化方案的实现也由草案的 canvas DPR 思路发展为离屏 `PixelPass`；文档应写明实际实现及其限制。

## 8. 供接手者参考的检查命令

在 worktree 中先检查状态并获取远端：

```bash
git status --short --branch
git fetch origin
git log --oneline --graph --decorate --all -20

```

`merge-tree` 只用于预览冲突；处理前先确认工作树没有未保存的其他改动。分支已公开推送后遵守仓库禁止强推、禁止 rebase 已推送历史的规定。不要把用户的本地运行配置、对话原始日志、依赖或构建产物加入仓库。
